Why exactly does Excel die?

  1. No real indexing — every filter scans the whole sheet.
  2. No safe concurrency — two people editing the same cell can corrupt data.
  3. No enforced rules — "fees must be > 0" is just a hope.
  4. Complex questions get painful — try "students who attended >80% but paid late" across 6 months.
  5. Weak audit and recovery — Excel assumes things go right. Databases assume things go wrong.
Excel isn't bad. It's just not designed for what databases are designed for.
Mindset

The mental shift: HOW vs WHAT

Same goal, two mindsets

Find all active students.

Python — say HOW
active = []
for s in students:
    if s.is_active:
        active.append(s)
return active
SQL — say WHAT
SELECT *
FROM students
WHERE is_active = 1;

No loops. No counters. You describe the result; the engine picks the strategy — which index, what order, whether to parallelize.

When you write a Python loop, you're locked into your strategy. If the data grows 1000×, your code still does the same dumb scan.

In SQL, the same query runs on 100 rows or 100 million rows. The engine picks a different plan each time — index scan, hash join, parallel workers. You didn't write any of that. You just described what you wanted.

That separation between "what" and "how" is the whole point.

History

SEQUEL → SQL: the name story

1
1974
IBM builds SEQUEL
Researchers at IBM create a language called SEQUEL — Structured English Query Language — for their experimental System R database.
2
~1977
Trademark conflict
An aircraft company already owned the trademark "Sequel". IBM had to drop the name to avoid legal trouble.
3
Late 1970s
Renamed to SQL
IBM shortened it to SQL — Structured Query Language. Same language. But the old pronunciation stuck.
4
Today
Both pronunciations win
Engineers at Google, Amazon, every major tech company still say "sequel". Some say S-Q-L. Both are correct.

The four pieces

📄
Pages
Rows live in fixed-size pages (~8 KB). The database reads and writes one page at a time, not one row.

Hot pages live in RAM. Disk reads are slow. Cache avoids them when you re-ask the same question.

Like a book's index. Jump straight to the right page in a few hops. Most common database index.
🎯

When you know the exact ID, hashing finds it in one step. Even faster than a B-tree.

Relational vs NoSQL

Relational
Strict tables, rows, columns, relationships
structure & correctness
  • Tables connected via shared identifiers (keys)
  • Strict schema — every row must fit
  • Strong ACID guarantees
  • Engines: Postgres, MySQL, Oracle, SQL Server
  • Best for: banking, accounting, anywhere data must be 100% accurate
NoSQL
JSON docs, key-value pairs, graphs
speed & flexibility
  • No strict schema — flexible structure
  • Related data often stored together (less joining)
  • Optimized for fast reads at scale
  • Engines: MongoDB, Cassandra, Redis, Neo4j
  • Best for: social feeds, real-time chat, caches, big analytics

OLTP vs OLAP

OLTP
Online Transaction Processing
day-to-day operations
  • Many users at once
  • Tiny, frequent queries
  • Fast response, strict consistency
  • Example: mark attendance, book a cab, place an order
  • Engines: Postgres, MySQL, Oracle
OLAP
Online Analytical Processing
analysis & decision-making
  • Few users (analysts, dashboards)
  • Huge scans across millions of rows
  • Optimized for aggregation, not consistency
  • Example: "average attendance by city over 5 years"
  • Engines: Snowflake, BigQuery, Redshift

Side by side

AspectOLTP — operationsOLAP — analysis

Data ageCurrent, liveHistorical (months, years)
Query typeSimple insert / selectComplex aggregations & sums
User baseEvery customer & employeeAnalysts & executives

Transactions — pay fees demo

Run the transaction

One user action, three database steps. Run the happy path, then crash it on purpose.

1
Deduct ₹5,000 from wallet
2
Insert payment record
3
Mark student "Fees paid"
Idle. Wallet ₹10,000, status: Not paid.

Before changing real data, the database writes its intent to a log on disk:

LOG: "About to change wallet 10000 → 5000"
LOG: "About to insert payment row id=789"
LOG: "About to update student status to 'paid'"
LOG: COMMIT

On crash + restart, the database scans the log:

  • If it sees COMMIT → reapply any unwritten changes.
  • If it doesn't see COMMIT → undo the partial changes.

That's the whole magic.

DDL vs DML — the house analogy

The two families you'll use most. One shapes the house; the other lives in it.

🏗️
DDL = architect & builder
structure · CREATE, ALTER, DROP
  • Build a room → CREATE
  • Change the plan → ALTER
  • Knock it down → DROP
vs
🛋️
DML = the resident
contents · INSERT, UPDATE, DELETE
  • Add a sofa → INSERT
  • Swap the TV → UPDATE
  • Throw out trash → DELETE
⚠️
DELETE vs TRUNCATE vs DROP: DELETE is DML — removes rows one by one, can be rolled back in a transaction. TRUNCATE is DDL — wipes the whole table instantly by resetting it, usually can't be undone. DROP removes the table itself, structure and all.

Database setup commands

The essentials

-- create a database
CREATE DATABASE tuf_sql_2;

-- list all databases
SHOW DATABASES;

-- switch into one (all later queries run inside it)
USE tuf_sql;

-- delete a database (irreversible!)
DROP DATABASE tuf_sql_2;

-- safe create: no error if it already exists
CREATE DATABASE IF NOT EXISTS tuf_sql;
DROP DATABASE is irreversible in most setups — it removes the whole database. Handle with care.
💡
Common mistakes: it's SHOW DATABASES (plural) but CREATE DATABASE name (singular). Mental model: a database is the whole filing cabinet, a table is a drawer, a row is a file. And there's no recycle bin — DROP DATABASE is gone for good, which is why pros often have DROP permissions removed.

Keys & relationships

A relationship links two tables via a primary key + foreign key. This is why we call them relational databases. Click a type.

Click a relationship type above.

Many-to-Many needs a junction table

A student joins many batches; a batch has many students. A third table in the middle holds the pairs.

students
student_id PK
name
enrollments
student_id FK
batch_id FK
batches
batch_id PK
batch_name
SELECT students.name, batches.batch_name
FROM enrollments
JOIN students ON enrollments.student_id = students.student_id
JOIN batches  ON enrollments.batch_id   = batches.batch_id;

Normalization = splitting data into related tables so nothing repeats. Store Raj's email once in students; his six fee rows just reference his id. Change the email in one place and every fee row stays correct. This avoids "update anomalies".

Self-referencing = a table points at itself. A mentor is also a student, so mentor_id is a foreign key back into the same students table:

SELECT s1.name AS student, s2.name AS mentor
FROM students s1
LEFT JOIN students s2 ON s1.mentor_id = s2.student_id;

Performance · Game

Indexing — the book at the back

How an index works

You saw the speed difference in the find-Aisha game. Here's what's actually happening.

An index is a separate, automatically-sorted mini-table holding two things: a sorted copy of the column (e.g. all emails A→Z) and a pointer to the real row. Because it's sorted, the database uses binary search — 1,000,000 rows might need only ~20 lookups instead of a million.

-- jump straight to a value instead of scanning
CREATE INDEX idx_user_email ON users(email);

-- one index covering two columns searched together
CREATE INDEX idx_name_city ON users(full_name, city);

Full scan vs index lookup

FeatureFull table scanIndex lookup
Search speedSlow (linear)Fast (logarithmic)
Disk spaceMain table onlyExtra space for the index
Insert speedFastSlower (must update index)
Best forSmall tablesLarge tables
💡
The hidden cost (write penalty): every INSERT, UPDATE, or DELETE must also update every index on the table. 10 indexes = writes roughly 10× heavier. Only index columns you frequently filter or sort by.

Filter · Playground

WHERE — the gatekeeper

WHERE checks every row: condition true → row stays, false → row blocked. It runs before SELECT, so you can filter on a column you don't display.

SELECT * FROM countries WHERE region = 'Asia';

✓ = row kept, ✗ = row blocked by the gatekeeper.

⚠️
Watch out: text needs single quotes (region = 'Asia'), numbers don't. Matching is usually case-sensitive. And you can't use a SELECT alias in WHERE — WHERE runs before the alias exists.

Combine · Playground

Logical AND / OR / NOT

Two conditions on every row. Flip the connector and watch which countries survive.

A: population > 50,000,000
B: area < 5,000,000 
SELECT * FROM countries
WHERE population > 50000000 AND area < 5000000;

The precedence trap

SQL applies AND before OR. Without parentheses you can get surprises — always group OR conditions.

-- "Accessories or Cables, AND under 20"
WHERE (category = 'Accessories' OR category = 'Cables')
  AND price < 20;   -- brackets force OR first
⚠️
Common mistakes: repeat the column each time — region = 'Asia' OR 'Oceania' is wrong; write region = 'Asia' OR region = 'Oceania'. And region = 'Asia' AND region = 'Oceania' returns zero rows — one row can't be two regions.

Sort · Playground

ORDER BY & LIMIT

Sort the rows, then keep only the top few. Classic "Top N" pattern.

Sort by
LIMIT 5 
SELECT country, area FROM countries ORDER BY area ASC LIMIT 5;
💡
Good to know: default is ASC (small→large, A→Z). LIMIT goes last in the query. You can sort by multiple columns — ORDER BY region ASC, area DESC uses the second as a tie-breaker. You can even sort by an alias.
Clean up · Playground

DISTINCT & AS (aliases)

DISTINCT removes duplicate values. AS renames a column header for the output (the real table is unchanged).

rename header (AS): 
SELECT DISTINCT region AS unique_region FROM countries;
⚠️
Common mistakes: DISTINCT goes right after SELECT. DISTINCT region, country dedupes unique pairs, not each column alone. And you can't use an alias in WHERE (it's created after filtering). Prefer underscores over spaces in alias names.

Module 5

Filtering essentials

Real data is messy — missing values, ranges, patterns. Meet the operators that handle it: IS NULL, IN, BETWEEN, LIKE (and their NOT forms).

IS NULL IN / NOT IN BETWEEN LIKE patterns Operator game

A deliberately messy users table

Look at the city column: real values, a NULL, an empty string, even a single space. That's why we need special operators.

NULL ≠ empty string ≠ a space ≠ zero. NULL means "unknown / not recorded" — so it can't be compared with = or !=.
Missing data · Playground

IS NULL / IS NOT NULL

Pick a column and a mode. Toggle normalization to treat empty strings and spaces as "missing" too.

SELECT id, email, city FROM users WHERE city IS NULL;
💡
The normalize trick: production data has missing values in many forms. NULLIF(TRIM(city), '') IS NOT NULL trims spaces, turns the result into NULL if it's empty, and only keeps truly-present values — folding NULL, '', and ' ' all into "missing".
Membership · Playground

IN / NOT IN

IN is a clean shortcut for many ORs. Pick cities to build the list, then flip IN ↔ NOT IN.

SELECT id, email, city FROM users WHERE city IN ('Delhi', 'Mumbai');
⚠️
The NOT IN + NULL trap: if the list has a NULL — NOT IN ('Delhi', NULL) — you get zero rows, because the DB can't prove a value isn't equal to "unknown". Keep NULLs out of NOT IN lists.
Ranges · Playground

BETWEEN / NOT BETWEEN

Inclusive range on last_purchase_inr. Both ends count. NULLs (never purchased) never match a range.

from to 
SELECT full_name, last_purchase_inr FROM users
WHERE last_purchase_inr BETWEEN 400 AND 800;
⚠️
Common mistakes: lower value first — BETWEEN 1000 AND 500 returns nothing. It's inclusive (both ends included). NULLs never match a range. With dates, '2025-12-31' means midnight, so events later that day get missed unless you include the time.
Patterns · Playground

LIKE / NOT LIKE

Type a pattern to match against email. % = any number of characters, _ = exactly one.

SELECT id, email FROM users WHERE email LIKE '%@tuf.com';
💡
Escaping wildcards: if your data literally contains _ or %, escape it with a backslash. LIKE 'test\_user%' matches a real underscore, so it finds test_user1 but not testXuser2.
