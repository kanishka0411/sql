Why SQL exists

Most people learn SQL by memorizing keywords. That's backwards. Let's start with the actual problem SQL solves.

1.2 — Why exactly does Excel die?

  1. No real indexing — every filter scans the whole sheet.
  2. No safe concurrency — two people editing the same cell can corrupt data.
  3. No enforced rules — "fees must be > 0" is just a hope.
  4. Complex questions get painful — try "students who attended >80% but paid late" across 6 months.
  5. Weak audit and recovery — Excel assumes things go right. Databases assume things go wrong.
Excel isn't bad. It's just not designed for what databases are designed for.
Lesson 2

The mental shift: HOW vs WHAT

SQL is declarative. You describe what you want, not how to get it. Most beginner pain comes from trying to think in loops.

2.1 — Same goal, two mindsets

Find all active students.

Python — say HOW
active = []
for s in students:
    if s.is_active:
        active.append(s)
return active
SQL — say WHAT
SELECT *
FROM students
WHERE is_active = 1;

No loops. No counters. You describe the result; the engine picks the strategy — which index, what order, whether to parallelize.

When you write a Python loop, you're locked into your strategy. If the data grows 1000×, your code still does the same dumb scan.

In SQL, the same query runs on 100 rows or 100 million rows. The engine picks a different plan each time — index scan, hash join, parallel workers. You didn't write any of that. You just described what you wanted.

That separation between "what" and "how" is the whole point.

Lesson 5

Transactions — pay fees demo

One user action, three database steps. Run the happy path, then crash it on purpose.

5.1 — Run the transaction

1
Deduct ₹5,000 from wallet
2
Insert payment record
3
Mark student "Fees paid"
Idle. Wallet ₹10,000, status: Not paid.

Before changing real data, the database writes its intent to a log on disk:

LOG: "About to change wallet 10000 → 5000"
LOG: "About to insert payment row id=789"
LOG: "About to update student status to 'paid'"
LOG: COMMIT

On crash + restart, the database scans the log:

  • If it sees COMMIT → reapply any unwritten changes.
  • If it doesn't see COMMIT → undo the partial changes.

That's the whole magic.

Lesson 7

OLTP vs OLAP

Same SQL language, very different engines. Pick the wrong one and everything is slow.

OLTP
Online Transaction Processing
day-to-day operations
  • Many users at once
  • Tiny, frequent queries
  • Fast response, strict consistency
  • Example: mark attendance, book a cab, place an order
  • Engines: Postgres, MySQL, Oracle
OLAP
Online Analytical Processing
analysis & decision-making
  • Few users (analysts, dashboards)
  • Huge scans across millions of rows
  • Optimized for aggregation, not consistency
  • Example: "average attendance by city over 5 years"
  • Engines: Snowflake, BigQuery, Redshift
